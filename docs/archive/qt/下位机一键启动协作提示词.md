你负责 Robot24 下位机 ROS2 工程，需要配合 Qt 上位机实现“一键启动整套系统”。请检查现有工程后实施下位机部分，提供可运行、可测试的接口和部署产物，不要只输出方案，也不要只添加一个 launch 文件。

## 一、背景与目标

上位机是无 ROS 依赖的 Qt 桌面程序，通过 TCP/JSON 与 `host_bridge` 通信。下位机已迁移至 ROS2，已有 `robot_bringup`、`robot_hardware`、`robot_safety`、`host_bridge` 和视频管理能力。请先核实实际包名、入口和运行状态语义。

目标使用流程：首次部署完成后，下位机通电联网，管理服务自动启动；用户打开 Qt，点击一次“启动系统”，即可完成预检、ROS2/控制桥接/档案所选视频模块启动，Qt 获取状态后显示“软件已就绪，待授权”。日常不需要登录下位机、手动 source、输入命令或逐个启动节点。

软件启动不得自动解除急停或隐式调用 enable/resume。保持现有初始化、使能、分组运行和安全许可机制，通信恢复不能恢复旧运动。

## 二、先检查并复用现有能力

1. 阅读工程约束、当前 README、ROS2 活动文档，以及整车 launch、运行管理、输入会话和视频服务实现。
2. 列出已有启动入口、配置来源、进程归属、就绪条件与缺少的接口；复用当前 ROS2 架构，避免另建控制管理器或维护第三套桥接。
3. 如果有上位机仓库，阅读 `docs/上位机ROS2适配与可靠性重构计划.md` 第 3、4、5 节；上位机侧可提供该文档，不能假设本仓库一定存在。
4. 输出简短实施说明后继续完成编码与验证。无法验证的现场事实单独记录，不阻塞可以离线完成的实现；不要改动无关的现有用户修改。

## 三、必须实现的下位机能力

### 1. 独立管理服务

- 提供随系统开机启动的管理服务及 systemd 部署文件，独立于 ROS2、`host_bridge` 和视频进程。在这些进程完全未启动时，管理服务仍能接收 Qt 的启动请求。
- Qt 直接连接管理服务；不能依赖控制桥接转发启动，也不能要求 Qt 拼 SSH/shell 或保存 root 密码。
- 采用适合 Qt 调用的网络接口，优先考察独立 TCP/JSON 管理协议与现有协议工具复用；如选择 HTTP/JSON，请给出理由并提交精确契约。先在文档中固定协议、端口、版本和认证机制，再实现，避免上位机猜测。
- 管理层只接受受控操作和档案标识，不能提供任意 shell 或任意文件写入接口；约束配置目录，日志不输出凭据。

### 2. 配置档案与预检

- 提供机器人 ID、档案 ID、配置 revision、运行模式及模块选择，支持 mock 与实机档案。
- 定义必需/可选模块与依赖，复用现有整车 launch 和视频服务，避免同一组件既由 launch 又由 systemd 重复启动。
- 检查配置、软件兼容版本、端口、所需设备、依赖和有效路径；在独立进程启动前加载正确的 ROS2 运行环境，不依赖操作者终端。
- 日常使用已部署的安装产物；启动按钮不触发源码编译、依赖下载或工作区安装。
- 返回结构化错误、失败阶段及处理建议。实机条件不足时明确失败，不擅自切换到 mock 后报告成功。

### 3. 异步启动、停止与恢复

- 一键启动按依赖完成预检、进程启动和健康检查；不能以进程存在、端口打开或固定 sleep 后没有报错作为整体 ready 的依据。
- 长任务异步执行，管理查询保持响应；设置各阶段时限，提供阶段进度和模块结果。
- 请求带 `request_id`；启动带 `robot_id/profile_id/config_revision`，返回 `operation_id`。重复请求、重复点击和并发请求不能创建第二套进程。
- Qt 断线或退出后，已接受任务仍可查询；重连后通过操作 ID 或机器人当前操作恢复进度，无需重新提交启动。
- 明确任务状态 `accepted/running/succeeded/failed/cancelled`；软件状态 `stopped/starting/ready/degraded/stopping/failed`。硬件初始化、使能、运行许可和急停单独返回。
- 失败时只清理本次创建的资源，保留日志；已有受管实例需要识别和核对，不误杀其他进程。停止时先确保运动停止，再逆序停模块，保留管理服务。
- 管理服务重启后对账服务管理器、实际进程、配置版本与持久操作记录，不能仅按旧记录宣告 ready。无法确认的操作返回结果未知/需要恢复，不自动重放可能产生副作用的动作。

### 4. 管理接口契约

至少覆盖以下语义，最终名称由接口文档固定：

| 语义 | 必需内容 |
| --- | --- |
| 握手与能力 | 管理协议版本、服务版本、机器人标识、支持能力、认证方式 |
| 档案查询 | 档案 ID、配置 revision、运行模式、必需/可选模块 |
| 预检 | 分项结果、错误码、失败原因、修复建议 |
| 启动/停止 | 请求 ID、操作 ID、目标档案、并发/重复语义 |
| 操作查询 | 状态、阶段、模块结果、可重试性、错误与时间信息 |
| 系统快照 | 软件状态、实际模块健康、配置/构建版本、控制端点、独立运行许可状态 |
| 日志读取 | 操作 ID、游标、数量上限、后续游标、日志轮转/过期语义 |

给出完整请求/响应 JSON 示例、字段类型、错误码、超时、重试规则，以及 Qt 从管理服务获取控制桥接地址后完成同步的顺序。协议中的命令接收成功与任务执行成功必须区分。

### 5. 配合 P0 控制可靠性

- 管理服务、慢 ROS2 操作和视频失败不能阻塞桥接心跳、收发及 watchdog。
- 检查 `host_bridge` 的输入 TTL、墙上时钟依赖、共享序号、多客户端控制权及运行状态变化触发会话重置的逻辑。不要把“去掉 TTL”作为最终修复。
- 上位机计划使用会话绑定、单调 watchdog、匹配心跳 ACK 和输入新鲜度协商；具体协议与 Qt 端对齐。若需要调整控制协议，提供版本/capabilities 变化和兼容说明，避免单方面改变字段后造成双方不兼容。
- 管理连接重连不能影响控制会话；控制连接中断仍按既有安全要求归零。管理接口不能成为绕过控制租约和运行许可的运动入口。

## 四、验证与交付

先完成无硬件 mock 验证，提供独立命令行客户端或脚本，让 Qt 尚未实现时也能验证完整管理流程。至少覆盖：

1. ROS2/桥接/视频都未启动时，从管理接口一次请求启动到实际就绪。
2. 重复/并发启动不产生重复实例。
3. 启动中客户端断线再连接，恢复原任务状态。
4. 无效配置、端口占用、缺少设备、必需模块超时，均返回正确失败并清理本次资源。
5. 可选视频故障按档案降级，不影响控制心跳和 watchdog。
6. 桥接崩溃后管理入口仍可用，能够查询与受控恢复。
7. 管理服务执行中重启，能对账进程和操作记录。
8. 启动/停止连续 20 轮，无孤儿进程、重复实例和端口残留。
9. 所有启动、恢复和重试均不隐式解除急停或调用 enable/resume。

交付代码、部署服务文件、示例档案、协议文档、模拟客户端、测试结果，以及一份“给 Qt 上位机开发端的对接说明”。对接说明明确端口、认证配置方式、请求示例、状态映射、控制端点发现方式、版本要求和未完成项。

默认仅在 mock/临时测试目录执行验证。真实系统服务安装、网络开放和实机运行遵循当前项目已有授权及部署规则；未执行的部署/实机验证明确记录，不能把测试通过写成现场已验收。

当前任务优先交付一键启动最小闭环；电机配置编辑、版本事务、应用与回滚可作为后续增量。先为档案与 revision 留出接口，不让后续配置维护需要推翻启动协议。

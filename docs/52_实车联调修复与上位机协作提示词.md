# 实车联调修复与上位机协作提示词

日期：2026-11-13。接续 [51 · 三组运动预设](51_三组预设与上位机对接提示词.md)。机器人端 build 标识为 `robot24-field-control-2`。本文前半部分可直接复制给上位机开发助手；后半部分是机器人部署和 ROS1 基线说明。

## 可直接复制给上位机开发助手的提示词

请修改现有上位机，完成以下控制 v2 协议对接，并交付代码、测试和简短说明。先阅读上位机自己的开发约束，保留现有 TCP 连接和管理 API 架构。不要只修改按钮文案，也不要把接口受理显示为动作完成。

### 1. 能力发现和控制状态

连接后仍接收 `hello`、`capabilities`，在三秒内发送控制 v2 的 `control_hello`。保持 `session_v2/freshness_v2/explicit_authorization/bounded_operations/isolated_output/runtime_permission` 等基础能力；三组多选仍协商 `motion_presets_v1`。

机器人端新增可选能力：

- `speed_level_v1`：显式五档速度控制。
- `latched_global_stop_v1`：独立 C++ 全局禁止和显式解除流程。

这两个能力加入客户端的 capabilities 列表，但不要拿缺少它们的旧服务端做静默兼容。缺少换档能力时禁用换档；缺少独立急停能力时提示机器人软件需更新，不宣称已具备新的急停保障。

`capabilities.speed_control` 包含 `command: set_speed_level`、`parameter: level`、`levels: [1,2,3,4,5]`、中立/重新授权要求及各档实际数值：

- `base_linear_m_s`、`base_angular_rad_s`
- `arm_linear_m_s`、`arm_angular_rad_s`
- `gripper_m_s`、`flipper_rad_s`

JSON 对象中的档位键为字符串。显示这些服务端值，不在界面另写一套推测速度。

`control_status.result` 新增/保留：

| 字段 | 含义 |
| --- | --- |
| `epoch` | 当前会话代数；状态同步请求允许使用旧 epoch |
| `speed_level` | 机器人实际采用的档位，UI 以此回显 |
| `authorized` / `operations_authorized` | 连续运动授权 / 操作授权 |
| `runtime_fresh` | 机器人运行反馈是否新鲜 |
| `runtime_global_inhibit` | 最近运行诊断中的 C++ 全局禁止标志；反馈过期时不能用缓存值判定已解除 |
| `global_stop` | 独立全局禁止 RPC 的执行状态，含 `state/ok/message/physical_stop_confirmed` 等 |
| `safety_halt` | 普通控制器清理 RPC 的状态，不能替代 C++ 全局禁止 |
| `safety_conditions` | 三类物理关联条件，详见第 5 节 |
| `presets` | 预设实际状态、诊断与许可，沿用文档 51 |

当前机器人默认开机为 **1 档**。机械臂各档请求速度为：

| 档位 | 平移 m/s | 旋转 rad/s |
| --- | --- | --- |
| 1 | 0.04 | 0.2 |
| 2 | 0.08 | 0.4 |
| 3 | 0.10 | 0.55 |
| 4 | 0.125 | 0.7 |
| 5 | 0.15 | 0.8 |

这些是笛卡尔请求速度；实际运动仍受关节限速、Servo、奇异位形和碰撞保护约束。

### 2. 显式换档

客户端将界面的档位按钮或快捷键翻译为以下 `system_command`。不要把数字键放进 `operator_input.keyboard.pressed_keys`，也不要在连续输入中附带 `speed_level`：后者现在明确返回 `USE_SET_SPEED_LEVEL`，不再静默忽略。

```json
{
  "type": "system_command",
  "protocol_version": 2,
  "session_id": "<当前会话>",
  "epoch": "<当前epoch>",
  "freshness_token": "<新鲜token>",
  "seq": 20,
  "ttl_ms": 300,
  "request_id": "<本次操作唯一ID>",
  "command": "set_speed_level",
  "params": {"level": 1}
}
```

`level` 必须是整数 1–5，布尔、浮点、字符串、越界值和额外参数均不接受。

换档流程：

1. 停止发送非中立输入，刷新会话，发送中立输入。
2. 取得 `authorize_operations`；没有 accepted/running 操作时提交换档。
3. 用 `operation_query` 等待终态。成功的 result 数组条目包含 `speed_level/epoch/authorized:false/operations_authorized:false`。
4. 再查询 `control_status`，确认实际档位。换档会清空旧输入、撤销两类授权并改变 epoch；操作可能同时显示 `invalidated:true`，这不等于换档失败。
5. 同步新 epoch/token，发送新的中立输入，显式重新授权后才恢复运动。

同一个 `request_id` 和相同参数可用于查询式重试，返回原操作；不能用新 ID 自动重复结果未知的操作。UI 先显示“换档中”，成功并读回后再更新档位。换档不自动恢复运动。

### 3. 急停及解除

急停发送独立报文：

```json
{"type":"emergency_stop","protocol_version":2,"seq":30}
```

机器人立即发零并异步请求 `/robot_runtime/global_stop`，此服务由独立 C++ guard 提供，绕过 Python 分组操作锁。同时尝试普通 halt 清理控制器；清理遇到操作忙，不会阻挡全局禁止。独立全局禁止调用失败时机器人保留急停锁存并重试，不能据失败回执自动恢复。

回执 `emergency_active:true/global_stop_requested:true/physical_stop_confirmed:false` 只表示本地锁存和请求已发起。随后查询 `control_status`：

- `global_stop.state` 可能为 `pending/running/succeeded/result_unknown`。
- 结合新鲜的 `runtime_global_inhibit:true`，显示软件运行许可已被禁止。
- 不把 RPC succeeded、速度命令为零或 `safety_halt` 成功显示为“实车已机械停止”。当前没有新增物理停止确认传感器，`physical_stop_confirmed` 保持 false。
- `global_stop` 是 RPC 记录；复位后判断当前禁止状态应读取新鲜的 `runtime_global_inhibit`，不能拿历史 succeeded 推断仍锁存。

空格或手柄急停组合键由客户端翻译为 `emergency_stop`；不要只上传 `space/l3/r3` 按键。普通组停止仍使用 `halt`，它与全局急停不同，操作忙时可能明确拒绝。

解除必须分步：

1. 操作员确认原因已处理；等待独立全局禁止确认成功、所有在途组操作结束及运行反馈新鲜。
2. 同步 epoch/token，发送中立输入，再发送顶层 `clear_emergency`（带标准会话/seq/token/TTL）。此步骤不需要先申请操作授权；急停期间操作授权本来就会被拒绝。未确认独立全局禁止时返回 `GLOBAL_STOP_UNCONFIRMED`。
3. `clear_emergency` 只清除桥接锁存，返回 `runtime_release_required:true`，此时 C++ 全局禁止仍然保持。
4. 重新发送中立输入、申请操作授权，再发 `system_command`，`command: reset_global_stop`，`params: {}`，使用新的 request_id。
5. 等待该操作终态。机器人要求实际诊断可读且新鲜、所有者心跳有效、C++ 已禁止、所有组不在 Armed/Running、没有组操作进行中；否则返回 `RUNTIME_NOT_SETTLED`。急停未清除时返回 `EMERGENCY_ACTIVE`。
6. 重新同步会话，核实全局禁止已解除；按实际状态显式 `recover → resume`，再发新中立输入和新授权。**复位本身不恢复 Running，也不恢复遥控授权。**

复位不得在 UI 自动重连流程、刷新定时器或急停按钮松开事件里自动执行。

### 4. epoch、授权和 TCP 调度

沿用文档 51 的顺序状态机：软件 ready → 控制握手 → 中立/操作授权 → init 完成 → 状态同步 → enable 完成 → 状态同步 → resume 完成 → 新中立/运动授权。

每次生命周期、模式和速度操作后，都重新读取实际运行状态。epoch 可能在操作完成响应后才通过运行广播更新；收到 `EPOCH` 时：

- 暂停运动，清除本地按住状态及旧 token；通过 `control_status` 取得新 epoch，再请求新 token。
- 重新发送中立输入，重新获得需要的授权。
- 只对明确被拒绝、尚未执行的请求按新会话重建；对 accepted/running/result_unknown 的操作先查询，不能自动换 ID 重发。
- 旧按键不能在恢复授权后自动重放；操作者须重新按键。

普通 heartbeat 不能替代 `freshness_request`；按服务端 `refresh_ms` 更新 token，连续运动输入建议 30 Hz，TTL 不大于 300 ms。网络读写、心跳、状态同步、operation_query 不能被某个长服务阻塞。客户端 TCP 建议开启 TCP_NODELAY；机器人端已开启。

模式切换使用 `system_command set_control_mode`，`params.mode` 为 `vehicle` 或 `arm`；不上传旧的 1/options 原始切换键。模式与预设选择是两个概念，预设多选仍按文档 51 实现。

### 5. 无传感器时的安全条件展示

ROS1 参考控制代码没有可靠的支撑接触、制动状态或载荷保持信号。当前不要从“电机在线”“角度到位”“关节速度为零”推断这些物理条件。

`control_status.safety_conditions` 返回 `condition/source_group/dependent_group/required_source/status/satisfied`。status 为 `unknown/satisfied/unsatisfied/expired/stale`。显示为：

- `arm_secured`：机械臂固定/制动证据；影响故障时底盘能否继续。
- `support_trusted`：摆臂支撑证据；影响故障时底盘能否继续。
- `payload_retained`：载荷保持证据；影响故障时机械臂能否继续。

缺失时显示“未接入/未知”，不能显示“已安全”。UI 不提供“强制满足”按钮，不发送 mock 条件注入服务。

现有策略并非“三条件必须都为 true 才能整车启动”：各组反馈正常且无相关限制时，可以整车运行；关联源组未准备或故障时，缺少物理证据会阻断其依赖组。因此没有这些传感器仍可做基础整车联调，但不能承诺源组故障后的独立降级继续运行。

### 6. 上位机验收

至少自动测试：

- 能力不足时禁用新增功能；服务端各档数值和实际档位正确回显。
- 换档必须中立、数值严格校验、在途操作冲突、旧输入和 token 失效、成功后需要重新授权。
- 初始化/使能期间急停不受操作忙阻挡；分别展示全局禁止与控制器清理结果。
- 急停 RPC 失败仍锁存、未知结果不当成功；未确认时不能清除。
- clear_emergency 不清除 C++ 禁止；reset 不自动恢复运动；禁止重连后自动 reset。
- EPOCH 在各相邻步骤间发生时可同步恢复，不重发结果未知的 enable/resume。
- 中立/停止输入、断线和重连不重放旧按键；物理条件 unknown/expired/stale 不显示为已满足。
- 不把软件模拟结果标为实车机械停止验收。

## 机器人端 ROS1 参数基线

用户已确认 reference 中 ROS1 参数可用。核对结果：

- `robot_canopen_config/config/legacy_joints.yaml` 与 `reference/ros1/Eyou_Canopen_Master/config/joints.yaml` 内容一致，节点 1/2/3/4/6/5、编码器比例和原轴参数已继承，不重复覆盖。
- 六轴/摆臂轨迹容差、履带几何及控制器约束已迁入，历史来源见 [37](37_ROS1实机参数迁入ROS2.md)。
- 本次将桥接机械臂五档速度恢复为 `reference/ros1/car_control/config/keyboard_teleop.yaml` 的数值，开机档位另取保守的 1 档。
- ROS1 夹爪旧速度的单位不能直接替换 ROS2 的 m/s，仍使用现有米制积分及 ±0.02 m/s 限速。
- reference 的旧 hybrid launch 指向的 `can_driver/config/can_driver.yaml` 和 PP 零点文件未完整保存在 reference 对应目录；不能据 launch 文件名伪造旧零点。当前私有 CAN 配置及原始参数需保留，涉及设备零点的写入另走受控维护。

新增 `tools/import_ros1_baseline.py` 将已确认的 ROS1 参数来源和 SHA-256 写入现场 baseline，使用 `ROS1:<joint>` 作为逻辑位置标签、继承方向确认。它不发送 CAN 帧、不改变设备参数、不使能电机，且拒绝覆盖已有输出。

仅生成参数基线副本：

```bash
python3 tools/import_ros1_baseline.py --output /tmp/robot24-ros1-parameters.yaml
```

此时设备身份仍为空、commissioned 仍为 false；ROS1 参数可用不能推导当前设备的序列号、固件及持久化读回。完成这部分仍需六轴真实只读导出，**不需要重新猜参数或重复试方向**：

1. 按 [28 的首次登记流程](28_CANopen软件交付与实机验收.md) 逐轴运行 `single_axis.launch.py`，在另一个终端执行不带 `--activate/--operation` 的 `axis_commission`，将每轴 JSON 输出保存为独立文件。切换轴前停止前一个主站，不能并行启动主站。
2. 汇总六份输出（包括 shoulder_yaw/shoulder_pitch 和四摆臂）：

```bash
python3 tools/import_ros1_baseline.py \
  --axis-readback /实际目录/left_front.json /实际目录/right_front.json \
    /实际目录/left_rear.json /实际目录/right_rear.json \
    /实际目录/shoulder_yaw.json /实际目录/shoulder_pitch.json \
  --output /实际目录/commissioning.yaml
```

也支持 `--snapshot /实际目录/runtime-snapshot.json`，输入为已有 `/robot_runtime/snapshot` 的 JSON message，或保存的 JSON Trigger 响应；冷机逐轴登记优先采用上一种方式。

仅当六轴 Node-ID、完整身份/固件和四项持久对象读回齐全时，工具输出 commissioned=true；模拟身份、缺字段和不匹配 Node-ID 都会拒绝。随后用 `baseline:=/实际目录/commissioning.yaml` 启动整车；管理部署则将该路径登记到 hardware profile。工具不会替用户写入 `/etc` 或替换正在运行的基线。

## 构建、验证与部署

本次代码使用既有 C++ `/robot_runtime/global_stop` 服务，不改变 Domain ABI；更新桥接 Python、配置和新增模块后需重启桥接进程。不要保留旧桥接进程或同时启动第二套 controller_manager。

```bash
source /已构建的核心安装/setup.bash
colcon --log-base /tmp/robot24-host-fix-log build --base-paths host_bridge \
  --build-base /tmp/robot24-host-fix-build --install-base /tmp/robot24-host-fix-install
source /tmp/robot24-host-fix-install/setup.bash

python3 -m unittest discover -s host_bridge/tests -v
python3 -m unittest discover -s tools/test -p test_import_ros1_baseline.py -v
ROS_LOG_DIR=/tmp/robot24-host-fix-roslogs python3 host_bridge/tests/ros_group_control_mock.py
ROS_DOMAIN_ID=96 ROS_LOCALHOST_ONLY=1 ROS_LOG_DIR=/tmp/robot24-host-p0-roslogs \
  python3 host_bridge/tests/ros_p0_mock.py
```

测试只打开隔离的本机端口及 ROS2 mock 域，不连接真实 CAN。真实制动、载荷保持、CAN 断线和机械停止时间仍须在现场记录，不能把软件许可撤销的耗时当成实车停止时延。

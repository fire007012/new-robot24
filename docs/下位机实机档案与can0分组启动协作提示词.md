## 1. 要解决的问题

当前上下位机默认在同一台主机运行，上位机经管理 TCP 9091 连接，控制桥使用 TCP 9090。下位机由 `linked-runtime/run_manager.sh` 启动，上位机连接 `127.0.0.1`。

现场已经接入底盘电机，但 Qt“运行环境”仍只有模拟。上位机侧只读检查发现：

- 当前 `linked-runtime/manager.json` 的 `config_root` 下只有 `mock.json`，其 `mode: mock`、设备列表为空，没有可被管理服务公布的 hardware 档案。
- 参考 `src/robot_bringup/launch/full_system.launch.py` 仍将 `canopen_interface` 默认设为 `canable0`、`private_interface` 默认设为 `canable1`。
- 参考 `src/robot_manager/manager.py` 的 `Backend.start(core)` 会传递 mock、baseline 等参数，但没有将档案中实际选择的 CAN 接口传入整车启动链路。

以上是已发现的配置和源码事实，不是对现场全部问题的最终结论。请核对实际部署是否与参考一致，避免只修改源码却继续运行旧安装包。

目标：管理服务实际公布可用的实机档案；Qt 选择实机及所需运动组后，预检和真实硬件启动使用同一组 CAN 配置，不能仍启动 MockSystem，也不能继续落到旧接口默认值。

## 2. 用户确认的接口规则

**分组测试默认接入 `can0`，不是只有底盘如此。**

| Qt 选择 | 底层组 | 分组测试默认接口 |
| --- | --- | --- |
| 底盘 `base` | base | can0 |
| 摆臂 `flippers` | flippers | can0 |
| 机械臂 `arm` | arm + gripper | can0，覆盖该预设实际需要的各后端 |
| 所选组的合法组合 | 所选底层组 | 默认仍按 can0，须核对协议和共享总线可行性 |

底盘/夹爪参考使用 CanDriverSystem，摆臂参考使用 RobotCanopenSystem，机械臂预设可能同时需要两者。请核对实际映射。不能只把一个后端改成 can0，而另一个仍隐式使用 canable0/canable1。

同一接口承载多个后端时，必须确认协议、节点标识、资源归属和主站行为可兼容，不要创建竞争主站。如果实际实现或接线不能支持某个组合在 can0 运行，应返回明确的预检错误、给出所需修正并完成可独立验证的部分，不能悄悄切换其他接口、启动全车或回退模拟。

该默认规则用于分组测试，不代表已经核验全车的总线拓扑。保留全车按真实接线显式配置的能力；必要时提供独立全车档案并说明 Qt 应选择哪份档案，不从“全选”按钮猜测物理接线。

## 3. 实施要求

### A. 提供真正的实机档案

1. 在实际管理配置源中部署 `mode: hardware` 的档案，保留原 mock 档案。通常可用 `profile_id: hardware`，但以工程既有契约为准。
2. 完整维护 robot_id、profile_id、config_revision、build_version、必需/可选模块、设备、组设备映射、真实基线等字段；版本须与实际安装、管理服务和发布清单匹配。
3. 分组测试所需 `devices/group_devices` 与 can0 规则一致，遵守现有 schema 和设备映射并集校验，不能只改某个显示名称。
4. 核对管理服务的 `profiles` 实际读取哪个源。若启用了配置事务，应处理活动 bundle、摘要和 revision：不能仅在原目录放一份 hardware.json，却仍从旧 bundle 只返回 mock。走受控部署/迁移，保留幂等记录和急停状态，不删除状态目录强制重置。
5. 停机部署后重新查询 `profiles`，确认确实返回实机档案及可用于 start 的 revision；不能仅以文件存在作为完成证明。

### B. 打通接口参数的完整链路

核对并按需修正：

```text
管理档案 + 本次 presets 选择
    → 管理预检 / 实际运行配置
    → Backend.start(core) 构造的 launch 参数
    → full_system.launch.py
    → hardware.launch.py / Xacro / ros2_control 参数
    → 实际所选硬件后端打开 can0
```

- 明确定义 CAN 配置字段及校验，复用已有字段时先确认其含义。传递显式参数，不依赖终端环境或历史默认值。
- `devices/group_devices` 的预检声明与实际启动参数必须来自同一份有效配置。只改接口名称列表、不改 launch 参数，不算完成。
- 检查真实模式最终为 `mock:=false`，加载实际硬件实现；mock 档案仍为模拟实现，不能全局强制实机。
- 按实际受影响包重新构建并安装，更新必要的部署摘要；核对 manager 的 setup 指向正确安装产物。不要让正确源码与旧安装包混用。
- 用户名不固定，启动脚本按自身位置或显式配置定位工程；命令使用 `~`、`$HOME` 或项目相对路径。旧 manager.json 中的绝对路径不能在换机后原样照搬，不输出令牌。

### C. 单组可以独立运行

1. 管理 preflight/start 沿用 Qt 现有 `presets` 参数：`["base"]`、`["flippers"]`、`["arm"]` 或合法组合，不要求 Qt 发任意 ROS 服务名或 shell。
2. 根据所选组核对所需设备、控制器和硬件后端；未选组未接电机、未初始化或普通轴故障，不应被误当成所选组必须失败的条件。
3. 单组运行不能因整车启动统一加载配置而偷偷打开其他接口、等待所有电机上线，或初始化、使能未选组。共享进程和后端可以复用，但生命周期与健康条件必须符合现有独立分组策略。
4. 机械臂预设仍包含 arm 和 gripper，两者状态分别核对，不将“部分成功”展示成整个预设运行成功。
5. 当前组的共享后端故障、全局急停、真实配置的物理联锁、watchdog、运行许可和显式授权约束继续有效。不能为了单组启动删除这些保护或伪造物理证据。

### D. 保持现有上位机接口和安全流程

- 管理协议仍为 v1，控制协议仍为 v2，保留 `motion_presets_v1`、freshness、两类授权、异步任务和原 ID 查询。
- 管理服务 start 仍只启动软件，不直接 init/enable/resume、不清急停；随后由 Qt 明确发出的分组操作按原协议执行。
- 硬件条件不足时返回可定位的错误码、阶段、实际接口和修正建议，不静默回退 mock，不以 TCP 连通、软件 ready 或命令受理代表电机允许运动。
- 找出并复用已有实际核验的电机协议、节点、波特率、方向、限值和基线。不猜测参数，不把模板 `commissioned: false` 直接改成 true，不自动写设备持久参数。
- 缺少现场资料时先完成源码、模拟测试和部署产物，列出缺失字段与确认方法；真实总线配置、系统服务变更和电机运动遵循下位机工程已有授权范围。

## 4. 测试与验收

先无设备验证，再按现场授权做实机联调。至少交付以下证据：

| 检查 | 预期结果 |
| --- | --- |
| profiles 查询 | 同时返回 mock 与实际部署的实机档案；revision、模式正确 |
| mock 启动回归 | 仍运行模拟，不打开真实 CAN |
| 单独 base | 预检和启动均使用 can0，只初始化/使能/运行底盘 |
| 单独 flippers | 预检和启动均使用 can0，不依赖未接底盘/机械臂 |
| 单独 arm | 所需后端均按 can0 规则处理，arm/gripper 分别确认 |
| 合法多组组合 | 接口和资源归属一致，组合许可完整；不支持的拓扑明确拒绝 |
| can0 不存在/未启用、配置冲突、缺真实基线 | 明确失败，不切到旧接口或模拟 |
| 源档案与活动 bundle/安装包不一致 | 正确更新或明确拒绝，不能报告实机就绪 |
| 急停、断线、停止及重新连接 | 保持归零、锁存和显式恢复，不自动恢复旧运动 |
| 全车配置回归 | 保留显式拓扑，不被分组 can0 默认值意外覆盖 |

无设备测试应检查实际构造的 launch 参数、最终硬件参数及后端接口选择，不能只断言 devices 列表为 can0。模拟中观测到的输出不能当作真实电机反馈。

实机阶段从底盘单组开始：Qt 选 hardware、仅 base、预检、明确启动、归中并授权，核对真实反馈与小幅运动，再验证停止/急停/恢复。未授权或未执行的实机项目列为待办，不写成已验收。

## 根因和实现

现场 `linked-runtime/manager.json` 关闭了配置事务，实际配置源 `linked-runtime/profiles` 原先只有 mock；源码中的 hardware 模板并未部署。管理服务未传 CAN 接口、未将 presets 转换为启动范围，launch/Xacro 则保留了 canable0/canable1 默认值。旧分组预检不能证明实际硬件的启动范围。

修复后的链路：

```text
hardware.can_interfaces + presets
 → group_selection.selected_groups（arm 展开为 arm、gripper）
 → can_config 校验 devices/group_devices 与后端所有权
 → preflight 使用所选组设备；拒绝未核验的共享总线
 → Backend.start：mock:=false、两个显式 interface、selected_groups
 → full_system.launch.py → hardware.launch.py
 → Xacro 展开后按安全策略裁剪 ros2_control 组件、轴
 → RobotCanopenSystem.can_interface_name / 每个私有轴.can_device
 → 仅所选控制器；组件初始 unconfigured
 → Qt 显式 init / enable / resume，runtime 拒绝未选组操作
```

CANopen 分组使用构建时生成的 `config/groups_flippers` / `config/groups_arm` 的 bus.yml、master.dcf、启动数据和 EDS。主站配置和驱动节点清单一起裁剪；整车仍用完整配置，只有一个 CANopen 主站。私有后端的电机列表也按组裁剪，避免同一组件初始化未选协议/电机。

`hardware` 的两个 CAN 字段均为 can0，四组 group_devices 均为 `["can0"]`，devices 并集为 `["can0"]`。可单独选择 base 或 flippers。arm 所需两个后端以及 base+flippers 等共享接口组合缺少现场兼容证据，目前明确以 CAN_TOPOLOGY 拒绝，直接 launch 同样防止绕过。不会切换接口、启动全车或回退 mock。

`hardware-full` 是独立显式拓扑模板。其示例 canable0/canable1 只保留历史接线能力，不能当作已确认接线。部署时只有提供 `--full-interfaces CANOPEN PRIVATE` 才发布全车档案；Qt“全选”不改变 physical topology，不应在 hardware 档案上全选后期待自动切换。

## 发布与受控迁移

修改包：robot_canopen_config、robot_hardware、robot_bringup；管理服务为独立 Python 文件。`robot_manager/deploy_can0.py` 是停机离线部署工具，需要管理 daemon 已退出并释放状态锁，且持久记录为 stopped、无资源、无未完成任务。它不启动 ROS。

工具保留 mock、令牌、旧操作 ID、状态目录与控制急停日志。基线以内容摘要命名复制，保持原内容；没有把 commissioned 改为 true。若配置事务启用，从活动 bundle 合并档案，生成新 bundle 和摘要、原子切换活动指针并记录审计；重复执行保持同一 revision。profiles 查询会检查活动 bundle 摘要，损坏时明确拒绝。

manager.json 的路径可相对其自身目录；档案 baseline 可相对 config_root。新 launcher 使用自身位置定位发布的 manager；不依赖用户名或调用 shell 的当前目录。部署要匹配发布目录中的管理程序、三个更新包、build_version 和 release.json，不能只覆盖源码。

离线迁移示例（从项目根目录运行；变量按实际部署填写）：

```bash
robot_ws="$(cd .. && pwd)"
robot_install="$robot_ws/linked-install"
robot_runtime="$robot_ws/linked-runtime"
# 先在 Qt stop 并确认 succeeded/stopped，无资源；退出管理 daemon。
# 构建/安装完成、生成与实际文件匹配的 release.json 后执行：
python3 -B "$robot_install/manager/deploy_can0.py" \
  --config "$robot_runtime/manager.json" \
  --setup "$robot_install/setup.bash" \
  --manifest "$robot_install/release.json" \
  --baseline "$robot_ws/commissioning/20261108-offline-preparation/commissioning.yaml"
# 只有已确认全车实际接线时才追加 --full-interfaces 实际CANopen接口 实际私有接口。
```

## 同机操作顺序

共同准备：启动管理服务后查询 hello、profiles；以 profiles 返回的 config_revision 发预检与启动。`robot_manager/client.py` 支持 `--presets`。不要把接口已 UP 或软件 ready 当作电机运动许可。

### 无设备模拟

```bash
robot_ws="$(cd .. && pwd)"
robot_runtime="$robot_ws/linked-runtime"
"$robot_runtime/run_manager.sh"
# 另一个终端，从源码根目录运行：
python3 -B robot_manager/client.py --token-file "$robot_runtime/manager.token" profiles
python3 -B robot_manager/client.py --token-file "$robot_runtime/manager.token" preflight --profile mock --revision 从profiles复制 --presets base
python3 -B robot_manager/client.py --token-file "$robot_runtime/manager.token" start --profile mock --revision 从profiles复制 --presets base
python3 -B robot_manager/client.py --token-file "$robot_runtime/manager.token" operation
python3 -B robot_manager/client.py --token-file "$robot_runtime/manager.token" snapshot
python3 -B robot_manager/client.py --token-file "$robot_runtime/manager.token" stop
```

Qt 选 mock 和所需预设；所有硬件插件为 MockSystem，不打开真实 CAN。需要运动仿真时仍走原显式授权与分组操作，模拟反馈不是实机证据。

### 单组 can0 实机

1. 按既有现场流程确认接线、协议、节点、波特率、方向、限值、基线及物理联锁；使用已有采集工具登记，不能仅修改 commissioned。管理 API 不配置接口波特率或设备持久参数。
2. stop 并确认；Qt 选 hardware，只选 base，使用 profiles 返回的 revision 执行 preflight。BASELINE、DEVICE、CAN_TOPOLOGY 等失败必须先定位处理。
3. 现场预检通过后 Qt 明确 start；管理 start 只启动软件，组件仍 unconfigured。
4. 归中、核对 freshness、两类授权和运行许可后，Qt 明确 init → enable → resume；核对真实反馈，再按现场授权做小幅运动。
5. 检查归零、停止、急停锁存、断线和重连；恢复必须显式重新授权，不能重放旧运动。
6. base 停机后才能换 flippers。arm 当前共享 can0 拓扑未验收，返回 CAN_TOPOLOGY；需要完成共享协议/COB-ID/资源所有权核验，或使用确认后的分离总线全车档案。

命令侧仅把模拟示例的 profile 换成 hardware、revision 换成实际返回值、presets 设为 base 或 flippers。不要在未通过现场验收时发运动命令。

### 全车实机

确认真实接线后部署 hardware-full，显式提供不同的 CANopen/私有接口及真实基线。Qt 选 hardware-full 和所需组合/全选，再依次 preflight → 明确 start → 归中授权 → 分组 init/enable/resume。它不继承 hardware 的 can0 默认值。未发布 hardware-full 时 Qt 不应提供一个可假定接线正确的全车流程。

## 分组启动后反馈误判的代码修复候选

2026-11-17，现场 hardware/base 的软件 start、init、enable、resume 成功后，记录到 `right_front_wheel_joint: private position feedback deadline exceeded`；wheel_controller 随后报告左右轮位置无效。故障后 can0 仍 ERROR-ACTIVE，错误及 BUS-OFF 计数为0。仅凭这些记录不能证明电机实际停止回包。

代码检查发现 `can_driver/src/can_driver_system.cpp` 的 grouped read 路径在获取互斥保护的反馈快照**之前**采样观察时间。RX 线程若在两者之间发布新反馈，快照中的时间戳可以晚于观察时间；位置有效性判断将产生 NaN，Freshness 也会按不可信时间触发 Stop，而报文实际可能仍新鲜。直接控制没有走这段 grouped ros2_control 检查，所以直接控制正常不排除这个缺陷。

候选修复已将观察时间采样移动到快照复制之后，保留原有反馈截止期限、稳定窗口、权限、故障锁存与所有电机参数。定向编译 `can_driver_system` 成功；未追加测试、未访问 CAN 或执行电机运动。现有日志没有保留触发瞬间的两个时间戳，因此这是已确认存在、可产生同类症状的代码缺陷，尚不能宣称现场故障已通过实机恢复验证。

本候选**尚未部署**。当前实际版本仍为 `robot24-field-can0-20261117-2`；暂存库为 `/tmp/robot24-feedback-snapshot-stage/lib/libcan_driver_system.so`，编译记录为 `/tmp/robot24-feedback-snapshot-build.log`。部署时需保持软件栈停止、备份原库、更新实际驱动库与匹配发布清单，再由使用者重新启动；不能只修改源码后继续使用原安装库。

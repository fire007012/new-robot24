# CSP 位置抖动根因与轨迹执行修复

日期：2026-11-08。继续追查记录 46 的 PH17/PH14 位置抖动。确认了本次 standalone 路径中的目标时序问题，并新增驱动内有限轨迹执行。PH17 已实测；PH14 只有历史抓包分析，尚未接入新入口复测。不能据此认定所有电机、整车或高频机械振动问题均已解决。

## 原因链与证据

1. `Motor402::setTarget` 把位置交给 `ModeTargetHelper` 保存；CSP 的 `ModeForwardHelper::write` 每个驱动周期将最近位置写入 `607A`。这是瞬时设定值接口，不是轨迹发生器，也不会从两个迟到的位置推断中间运动。
2. 原 PH17 测试程序每次 target 创建客户端，等待应答后再额外等待约 20 ms。实际更新间隔中位数约 40 ms、最大约 124 ms，而 SYNC/驱动周期为 20 ms。电机因此收到保持旧位置、再跳到新位置的阶梯目标；单位周期位置增量忽小忽大，形成反复追赶。
3. 记录 46 在同一 50 Hz 配置、相同线性 ±90°/3 秒轨迹下，只修正客户端定时，就将反馈速度标准差从 0.208/0.244 降到 0.006285/0.006182 rad/s。用户现场确认“明显减轻”。这支持时序问题是本次 PH17 抖动的主要因素，而非仅终点误差或 CAN 错误。
4. `/tmp/ph14-05-90-check` 历史位置测试也在服务应答后额外等待 15 ms。抓包中取首段轨迹 target 后约 1–11 秒：500 个 `0x202` 位置目标帧中有 **118 个相邻重复目标**，变化间隔中位数约 20.8 ms、最大约 42.7 ms。证明 PH14 发出的目标序列也有同类缺陷，但尚不能量化新入口对这台电机的改善程度。

速度模式对这个问题不敏感的原因是：恒定速度命令被重复发送，仍然是同一个速度；位置运动需要每周期连续变化的位置目标。不是 CANopen 天生无法平稳定位，也不能从这些证据推断电机增益已经合适。

只给 Python 加固定频率仍依赖用户进程和逐点 ROS RPC 调度，所以继续修复了轨迹的执行归属。

## 实现

- 新增 `COPositionTrajectory` 服务：一次接收完整位置/时间数组；空请求只查询当前命令会话 epoch。新请求必须携带该 epoch，防止停止/恢复后迟到旧请求重新运动。
- 在驱动写周期中、`motor_->handleWrite()` 前，按 steady clock 取样完整计划并写目标。各段使用五次 rest-to-rest 插补，上层不再决定逐点节拍。
- 显式启用，限定 standalone CSP 8；设备反馈健康、模式已确认、已建立命令会话且静止时才接收。限制起点误差、段时长、总时长、位置数值范围，以及配置的轨迹峰值速度/加速度。
- 运行中拒绝 scalar target 和新计划覆盖。停止、会话变化、失去健康反馈或 deactivation 后计划失效；写周期超过 100 ms/时钟回退会丢弃计划并进入原 halt 异常路径。单元测试覆盖取消后不重放。
- [test_canopen_csp.py](../tools/test_canopen_csp.py) 默认走完整计划入口；旧逐点路径保留为显式 `--execution stream` 的诊断选项。

服务语义与配置详见 [POSITION_TRAJECTORY.md](../ros2_canopen/canopen_402_driver/POSITION_TRAJECTORY.md)。此次 PH17 配置显式启用，最大轨迹速度 1 rad/s、最大轨迹加速度 1.5 rad/s²，仍为 50 Hz。没有修改电机增益、零偏、限位或保存对象。

该服务接受的是有限计划，接收后可在提交客户端不再发送乃至退出时继续完成已授权计划；最终保持末位置，停止失能仍显式调用 halt/disable。它不是停发即停的 streaming deadman。操作系统调度与 SYNC 仍可能抖动；这次没有把驱动改成硬实时或 SYNC 锁定执行，也不承诺消除全部物理振动。

整车已有 `RetainedJointTrajectoryController`，继承标准 JointTrajectoryController，controller_manager 配置为 200 Hz，由控制器产生每周期目标；`RobotSystem` 经组权限、限位和 epoch 检查后调用 `set_target`。本次不在这条路径叠加第二个轨迹执行器，`managed_by_ros2_control: true` 时新入口拒绝激活。未完成整车的实际周期和运动平稳性复测。

## 验证结果

本轮 Node-ID 1 的 PH17、`V140-0264`；真实模式能力 `6502=0x03CD`，不启用 PH14 零能力掩码兼容。沿用此前构建的主站/基础通信包，新编译 `canopen_interfaces`、`canopen_402_driver`，产物 `/tmp/csp-root-install`。

完整计划测试一次提交 `[起点, 起点+90°, 起点]`、时间 `[0,3,6]`，运行中没有接受后续逐点目标：

| 检查 | 结果 |
| --- | --- |
| 完整计划运动 | 已到达正向峰值附近并返回，50 Hz 反馈采样峰值约 **89.99108°**，回程相对起点 **−0.000163°**；顶点未额外停留，不能用该采样峰值认定精确停止于90° |
| 两个运动中段 CAN 目标 | 各 **110 帧**，相邻重复目标均 **0**；帧间隔中位数约 20 ms，最大分别约 22.66/22.55 ms |
| 超速度/加速度计划 | 被拒绝，未开始该计划 |
| 执行中的 scalar target、新计划覆盖 | 均被拒绝 |
| halt/disable 后重新建会话，提交旧 epoch | 被拒绝 |
| 中途停止并重新使能，已取消计划不重放 | 观察约 0.8 秒，位移约 **−0.000054°**；未继续旧计划 |
| 该组合测试最终状态 | `passed=true`，状态字 0x0250、速度 0、故障 0 |

首次验证在 0.3 秒 DDS 发现窗口内没收到反馈，使能前退出；证据保留。测试入口改为最多等待 5 秒发现首帧，运动中反馈期限仍为 100 ms。

随后仓库默认工具再次完成同样 ±90° 计划，`motion_passed=true`，但 halt/disable 后的单次 SDO 速度为 **62 count/s**（约 0.000059 rad/s），故其严格零速汇总 **`passed=false`**。没有放宽阈值或把该次结果改成通过。最终退出主站并恢复参数后的真实读回速度为 **0**、状态字 **0x0250**、故障 **0**。短时反馈零速噪声及停止稳定时间仍应独立验证。

新增轨迹数学/完整计划采样、非法/超限输入、epoch/健康失效、时钟与写周期超时、覆盖拒绝回归；同时扩展 managed 命令测试，最终驱动 **5 个 CTest 入口全部通过**。初次测试误用了未完成安装的旧库和不可写 ROS 日志路径，纠正环境后复跑通过，失败日志保留。最终小幅整理将配置合法性校验移到启动轮询前、消除测试编译警告，并避免未运行计划时新增额外健康/epoch查询；重新构建并运行上述5个入口。未重跑整个工作区回归。

由于公开驱动头文件有变化，另外重新构建了依赖的 `canopen_ros2_control` 与 `robot_canopen_config`，避免新驱动与旧插件布局混用。控制插件 **2 个**、配置 **4 个** CTest 入口也全部通过，连同驱动共 **11 个入口通过**；这仍然是软件回归，不是整车200 Hz实测。

## 最终设备与证据

主站已退出，恢复原心跳、插补周期、模式和全部 PDO；本轮前后对象比较仅实际位置 `6064` 变化，零点、限位及其余备份对象一致。90 个 PDO 恢复写入成功应答，CAN 最终收发错误、error-warning、error-passive、bus-off 均为零。

原始 CAN 帧、历史 PH14 源证据、正负向请求结果、反馈、恢复读回、构建/测试日志和代码快照位于 [20261108-csp-root-cause](evidence/20261108-csp-root-cause/)。源码快照包含记录45及工作区原有未提交修改，不是发布提交。PH14 新路径、整车、200 Hz、进程失效停止及机械振动频谱均未因此验收通过。

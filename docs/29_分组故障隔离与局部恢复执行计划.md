# 分组故障隔离与局部恢复执行计划

日期：2026-10-25；软件验收更新：2026-10-26。状态：P0–P5 软件实现及离线验收完成；P6 实机验证和匹配版本发布待现场执行。整车入口默认启用分组 group_policy；直接启动底层硬件入口且策略为空时保留 ROS2 全局联锁诊断模式。

第一阶段触发点审计和模型结果摘要保留在 [记录 30](30_分组事件合同与第一阶段实施记录.md)；后续两个原生插件、分组协调、输入会话隔离、维护和进程故障验证见 [实施验收 31](31_分组隔离与局部恢复实施验收.md)。软件验证不代替真实制动/停止和机械关联条件的现场证据。

对应需求：小范围异常不应默认导致全车无法操作；故障处理需要按严重程度、运动组及机械关联关系决定停止和恢复范围。

当前发布基线为主仓库 `2f94294`、`ros2_canopen` `78242f5c`、`can_driver` `0ba4e61`。该基线的旧离线测试只证明了全局联锁行为，不能作为分组策略证据。2026-10-26 已完成当前工作树分组策略的空前缀构建、原生插件及 Humble 整链和搬迁回归，原始批次产物已清理，结果摘要及重跑命令见实施验收 31；三个匹配提交和发布标签仍待 P6 实机通过后生成。

## 1. 目标与保留约束

目标是允许满足条件的健康组独立启动、保持运行和恢复。一个组不可用时，应报告故障范围、关联限制及可用操作，避免把整车描述为一个不可区分的 Fault。

继续保留：

- 一个 controller_manager、两个硬件组件；CANopen 总线仍只有一个主站。运动组可以跨后端，不按组另起 CANopen 主站。
- 六轴机械臂共用一个 JTC；其中一轴不能运动时，中止整条机械臂轨迹。
- 首次使能同步反馈、位置保持/速度归零、命令有限值和范围校验、单一写入者及命令 epoch。
- 故障恢复不自动恢复旧轨迹或旧速度。故障组需要重新就绪、显式启动和新命令；未受影响组的有效会话不因其他组恢复而失效。
- 无可信反馈、未知制动/姿态或未分类驱动错误不能自动视为可继续运行。
- 诊断、状态读取、故障确认及受控维护与运动许可分别管理；设备不可读时明确报告，不返回缓存值冒充当前读回。

## 2. 运动组与故障传播范围

| 运动组 | 关节与控制器 | 默认停止范围 |
| --- | --- | --- |
| `arm` | 两肩轴 + 肘/腕四轴，`arm_position_controller`，跨两个后端 | 六轴机械臂及明确依赖它的组 |
| `flippers` | 四摆臂，CSV/CSP 两个互斥控制器 | 默认停止四摆臂及受车体稳定性影响的组 |
| `base` | 两履带电机，`wheel_controller` | 两履带共同停止，防止单边继续驱动 |
| `gripper` | 夹爪，`gripper_controller` | 夹爪执行确定的保持/停止策略；必要时联锁机械臂 |

先以四个组为实现边界。四摆臂内的单轴降级运行另作明确的调试/维护能力，不能默认让剩余三轴继续执行原联动。

需要区分三类范围：

1. **设备范围**：哪个轴、控制器或通信通道发生异常。
2. **任务范围**：正在执行的任务需要哪些轴；六轴轨迹包含两个后端，但不天然包含底盘和摆臂。
3. **机械关联范围**：姿态、制动、支撑、载荷等条件要求哪些其他组共同停止。

总线故障覆盖使用该总线的轴，再根据组和机械关联扩大。例如 CANopen 总线故障影响两肩轴及四摆臂，机械臂因此整体停止；底盘能否继续由姿态/支撑条件决定。单个夹爪轴故障不直接等价于私有 CAN 总线失效。

### 关联矩阵

建立版本化配置，记录 `source_group`、故障类别、关联组、允许继续的必要条件、信息来源和未知时的处理。

初始原则：

- 机械臂失控或制动/姿态不可信时，底盘停止。
- 摆臂故障导致支撑状态不可信时，底盘停止。
- 夹爪故障且载荷保持状态不可信时，机械臂暂停相关动作。
- 在姿态、制动、支撑等条件有可信依据时，才允许相应健康组继续。

现场尚无传感器或驱动反馈能够证明的条件，标为未知并阻断对应依赖组。软件不伪造“稳定”“已制动”等状态。矩阵的物理依据在实机阶段确认，执行引擎和未知状态处理先离线验证。

## 3. 事件分级与处理规则

| 事件 | 目标处理 | 恢复方式 |
| --- | --- | --- |
| 非法新目标、参数错误 | 拒绝该请求，记录原因；不影响无关任务 | 修正请求，无需整车 recover |
| 速度话题停发 | 对应控制器按既定超时归零/保持 | 新的有效命令；停用后重启仍需新会话 |
| 已运行控制器产生非有限值或非法输出 | 停止其所属运动组，报告命令源错误 | 修复命令源并显式重建该组会话 |
| 周期抖动、尚未超出可信新鲜度上限的通信延迟 | 告警、计数；按可验证规则处理 | 依据稳定窗口撤销告警 |
| 反馈超过可信上限、心跳超时、非预期失能/模式变化 | 立即撤销受影响组会话，执行关联矩阵 | 状态稳定并重新校验后，仅恢复该组到 Armed |
| 已知 EMCY | 按设备型号、固件及错误码映射到处理级别和范围 | 满足该错误的明确恢复条件 |
| 未分类 EMCY | 默认停止故障轴所属组，按关联矩阵扩大范围并保留原码 | 完成诊断或明确恢复；禁止静默忽略 |
| 单条 SDO 失败 | 区分只读诊断、维护和运动准备；仅使依赖该结果的操作/组失败 | 有界重试或明确恢复，不能默认重建全车 |
| 保存/回滚结果不确定 | 锁定受影响轴及其依赖组的运动许可，保留 journal | 身份校验、明确恢复和读回；其他组按关联条件运行 |
| 急停、控制进程整体失效或无法界定范围的全局危险 | 全局停止 | 保留统一恢复要求，显式确认和新命令 |

EMCY 分类必须依据设备资料或可验证记录；当前没有依据的错误码先使用组停止。已有心跳超时、硬故障及反馈可信上限到达事件直接处理，不再叠加额外延迟。

通信配置区分告警阈值、停止阈值和恢复稳定窗口，按后端、轴及反馈类型配置。恢复采用滞回以避免反复启停；Warn 期间的运动仍须满足明确的新鲜度上限。不能只把当前 100/500 ms 阈值统一放大，也不能以连续漏帧计数替代时间上限。

## 4. 实施阶段

### P0：冻结事件合同与回归样本

- [x] 审计当前所有 `fault()`、`report(false)`、`return ERROR`、全量 `halt/recover/verify` 和控制器数量检查。
- [x] 将每个触发点映射到轴、组、共享资源、严重程度、停止动作、恢复条件和可用诊断。
- [x] 明确四组所有权、控制器资源、任务依赖及关联矩阵的默认未知行为。
- [x] 整理可继续操作与必须停机的代表用例，并保留旧全局策略作为对照。

**产物**：事件/关联配置规格、状态转换表、验收矩阵；不得把尚未确认的物理条件写成 true。

### P1：重构共享许可与状态模型

主要位置：`robot_safety/include/robot_safety/domain.hpp`、`robot_safety/src/domain.cpp`、对应单测。

进度说明：分组模式下两个原生硬件写入者均已迁移到具体组许可；模型、原生插件和 Humble 模拟整链均有回归。未显式指定策略的旧全局模式保留。

- [x] 用轴/组的 ready、状态、原因及 epoch 替代两个后端的单一 ready 和全局运行 epoch。
- [x] 保留独立全局急停/禁止运动状态；组许可还需满足关联条件及全局许可。
- [x] 定义事件字段：来源轴/组/后端、错误码、严重程度、时间、证据有效性、恢复条件。
- [x] 实现确定的故障传播与去重；同一事件反复上报不反复重建健康组会话。
- [x] 整车状态改为组状态的汇总，可表达部分运行、部分受限；业务写入必须检查具体组许可。

**出口**：一个组故障或恢复不会改变无关组 epoch；全局停止能撤销全部组；未知关联条件按矩阵阻断。

### P2：让硬件错误范围与组许可一致

主要位置：`ros2_canopen/canopen_base_driver`、`canopen_402_driver`、`canopen_ros2_control`，以及 `can_driver` 的 SystemInterface。

- [x] 分离共享资源故障与单轴故障；单轴 boot、身份、PDO 或反馈失败形成该轴的不可用状态，继续初始化其他可用轴。
- [x] 修改逐轴 read/write，缺少驱动、失效状态或拒绝命令的轴不再直接使整个组件所有接口失效；相应组的写入在硬件周期内关闭。
- [x] 按组在两个后端同时撤销机械臂目标，不能只等待 Python 监控稍后停控制器。
- [x] 对局部故障保持硬件组件可服务，Humble `ERROR` 仅用于确实使组件共享资源失效或实现不能继续安全服务的故障。
- [x] 保证故障组 stop 请求可以释放本地控制器资源；设备停止失败仍要记录，不因等待失联轴而阻塞所有健康组切换。
- [x] 审计共享 CAN 传输失败在各组间的传播、启动失败的可重试性及停止动作的时延/阻塞行为。
- [x] 保留每轴反馈有效标志；不可用轴不返回伪造正常状态，也不使健康轴的读取一并失败。

**重要约束**：仅修改 `robot_safety` 中的全局 Fault 判断不够。当前 SystemInterface 的 `ERROR`、全量初始化和 DeviceContainer 的单节点 boot 失败传播，都可能让 Humble 回收整个组件接口，需要在本阶段一起解决。保持唯一主站，不能为隔离故障复制 DeviceContainer。

**出口**：一个模拟轴掉线时，故障组关闭、关联组按策略停止，允许继续的组仍能完成 read/update/write；停止控制器不因故障接口不可用而卡死。

### P3：实现按组启动、停止与局部恢复

主要位置：`robot_hardware_runtime/coordinator.py`、`node.py`、ROS2 服务定义和启动配置。

- [x] 增加明确的组选择及操作接口，支持单组或多组 init/enable/start/halt/recover；保留全车入口用于明确的全局操作。
- [x] 区分硬件组件生命周期、单轴 CiA402/私有协议使能状态、运动组 Armed 和控制器 Running。
- [x] 只对选定组及其必要依赖做身份/PDO/反馈检查和轴初始化；不为底盘单独运行而要求所有机械臂/摆臂轴就绪或使能。
- [x] 对共享后端采用轴级准备和控制，不通过反复 deactivate/reconfigure 整个组件实现普通局部恢复。
- [x] 局部 recover 最终只将相应组恢复到 Armed；健康组控制器、轨迹和 epoch 保持有效。
- [x] CAN 主站/传输确实需要重建时，先停止使用该共享资源的全部组，再执行资源恢复；不默认重建另一条健康总线。
- [x] 为长操作设置范围内互斥、超时和操作编号，处理迟到响应；不能用一个全局锁长时间阻塞所有诊断或无关组操作。
- [x] 故障状态继续提供组状态、错误原因、可执行操作及受控恢复；对离线设备明确报告不可读。

**出口**：不要求四类控制器同时 active；底盘独立启动、机械臂停止后其他许可组继续、单组恢复均有进程级回归。

### P4：更新控制器、维护和监控调用路径

- [x] 将监控中的“恰好四个活动运动控制器”改为检查已请求组的预期控制器与资源所有权。
- [x] 摆臂 CSV/CSP 切换只停止和重建摆臂会话；六轴机械臂跨后端仍按整组切换/取消。
- [x] 速度超时、非法新请求及控制器主动停用按事件合同处理，避免普通操作触发全局 Fault。
- [x] 将维护 journal、dirty、restore 和基线校验限定到目标轴及关联组；共享 SDO 通道继续单飞。
- [x] 维护动作在满足联锁时允许其他组继续；需要共享资源重建或无法证明机械独立时，明确扩大停止范围并说明原因。

**出口**：摆臂切换不重启底盘/机械臂；夹爪命令停发局部处理；一个轴的维护不确定结果不会通过一个全局 dirty 无条件封锁所有组。

## 5. 最低离线验收矩阵

| 场景 | 必须观察到的结果 |
| --- | --- |
| 底盘单独请求启动，机械臂未请求/不可用 | 仅校验所需资源及关联条件；条件满足则底盘可启动，未请求轴不自动使能 |
| 夹爪速度命令超时、非法新请求 | 对应控制器归零/保持或请求被拒绝；无关组不被全局锁定 |
| 周期抖动、短暂 PDO 延迟 | 在可信上限内按告警合同处理；到达停止上限则停止受影响组，不能无限沿用旧运动命令 |
| 普通驱动告警、已知/未知 EMCY | 匹配配置级别；未知码至少停止所属组，保留原始信息，不静默放行 |
| 肩轴或私有机械臂轴持续故障 | 六轴机械臂共同停止并终止当前轨迹；允许继续的其他组保持原会话 |
| 任一履带轴故障 | 两履带共同停止，防止单边驱动 |
| 姿态、制动或支撑条件未知 | 对应依赖组被明确阻断，诊断说明条件与来源 |
| CANopen 总线失效 | 停止受影响轴所属组及关联组；保持唯一主站；不无条件重建私有总线 |
| 一个组局部恢复 | 该组仅到 Armed，需显式启动和新目标；健康组控制器和 epoch 不变 |
| 恢复失败、部分成功或响应迟到 | 不重新开放旧会话；已确认健康且无关联的组不中断；操作结果可定位 |
| 目标轴维护或保存超时 | 目标及依赖组受限，诊断/restore 可用；健康独立组按条件保持运行 |
| 全局急停 | 全部组停止；任何局部 enable/start 都不能绕过全局禁止 |
| 无效配置、组/控制器资源冲突 | 在开放运动前拒绝，说明错误；不通过隐式降级或隐藏失败继续启动 |

## 6. 建议提交顺序

1. 文档和事件合同：冻结分组、关联条件、错误分级和测试用例。
2. `robot_safety`：按组状态、epoch、全局禁止及事件传播单测。
3. 两个硬件后端：轴级可用性、局部错误传播、资源释放和节点启动失败隔离。
4. 运行协调层：按组生命周期、准备/使能和局部恢复接口。
5. 调用层：监控、摆臂切换、维护 journal 与诊断工具。
6. 离线整链和文档：故障注入、空前缀验证、证据与验收单。
7. 实机验收通过后，发布相互匹配的子模块及主仓库提交。

依赖关系为 P0 → P1 → P2 → P3 → P4 → P5 → P6。每阶段应有可独立审查的提交；中间迁移状态保持原有保守许可，功能组合同尚未完整接入前不单独放开总开关。
